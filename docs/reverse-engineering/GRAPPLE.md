# Grapple — behavioural specification

Scope: everything that happens between the player pressing the grapple button and the player being back
under normal movement physics: input path, targeting, acceptance, attachment, the pull while attached,
release, momentum, the grapple budget and its refills, interactions with the other abilities, camera and
feedback effects, and the Kismet events the grapple fires. Companion documents:
[`ABILITIES.md`](ABILITIES.md) (walking, jumping, landing, power jump, rocket boots, death/checkpoints) and
[`NATIVE_PHYSICS.md`](NATIVE_PHYSICS.md) (the native pawn physics everything runs on).

**Publication rules followed.** The rules below were derived by reading, locally and only locally, the
UnrealScript source text that ships inside the cooked packages (`TextBuffer` `ScriptText` objects), the
class default objects (CDOs) and the native executable. No source text is reproduced, quoted or
transcribed here; behaviour is described in our own words as rules, decision tables, timelines and
formulas. Names of classes, functions, states, properties and tags, numeric constants and native
addresses are published as facts. This document was adversarially re-verified (section 19).

## Most important findings (read this first)

| # | Finding | Confidence |
|---|---|---|
| 1 | The grapple is **not a rope**. There is no length constraint and no pendulum swing: while attached, the pawn is in native **`PHYS_Flying`** (no gravity) and the gun adds a **pull toward the anchor of magnitude `10⁷ / d` uu/s²** (d = pawn-centre-to-anchor distance in uu) on every gun tick. | CONFIRMED (src+bc) pull; CONFIRMED (native) no gravity in flying |
| 2 | **The flying physics caps speed at the pawn's `AirSpeed`, which the gun sets to `fGrappleAccel` = 2000 uu/s**, and applies drag `(1 − 0.15·dt)²` per tick. The pull is added *after* that cap in the same frame, so the stored speed is a sawtooth between 2000 and 2000 + `dt·10⁷/d`. `fGrappleMaxSpeed` (10 000) is never read. | CONFIRMED (src, native `APawn::physFlying @ 0x100AE1710`, cdo); sawtooth STRONG (tick order §15) |
| 3 | No steering while attached: the `Grappling` controller state hands the pawn a **zero acceleration** and discards jump presses; mouse look still works. | CONFIRMED (src) |
| 4 | **Automatic release when the pawn centre is closer than 200 uu (`fGrappleReleaseDistance`) to the anchor; the velocity is halved at that moment.** Releasing the button keeps the velocity unchanged. | CONFIRMED (src+bc, cdo) |
| 5 | Range: a hit counts only if it is **closer than 5000 uu (`fMaxDistance`) to the eye**; the trace itself is 16 384 uu long. | CONFIRMED (src, cdo) |
| 6 | Budget: firing needs `used < capacity`; each attach costs one; **any landing refills** (except on floors tagged `NotLandable`); a charged `ASAMURechargeCrystal` refills; capacity starts at **0** and Kismet sets it per level (values in the maps: 0, 1, 2, 3). Capacities ≥ 4 behave as unlimited. | CONFIRMED (src, cdo, map decode) |
| 7 | Release-instant targets (`ASAMUReleaseGrappleInstantInterface`: recharge crystals, glow flowers) attach, suppress the pull and auto-release after a 0.05 s gun timer. | CONFIRMED (src, cdo) |
| 8 | The anchor follows the hit actor **only if it is an `InterpActor`**; on anything else (including moving `DynamicSMActor`s such as `ASAMUFloatingRock`) it stays at the world-space hit point. It follows **rigidly**: the actor's translation and its turn about its own location (G-AT-8). | CONFIRMED (src); the rigid riding CONFIRMED (native) and measured |
| 9 | Release speed is **frame-rate dependent**: proximity release halves a velocity that already contains the last pull increment (≈ `50 000·dt` uu/s near 200 uu); a button release hands over up to `2000 + dt·10⁷/d`. | CONFIRMED (src) arithmetic; magnitudes are model predictions to verify by trace |
| 10 | No cooldown: the "just released" flag clears on the next gun tick. A re-press while the weapon is still in its firing state waits for the next 0.1 s refire check. | CONFIRMED (src, incl. stock `Engine.Weapon`) |
| 11 | Frame order is now **STRONG**: input → map-placed actors → player controller → pawn (physics) → power-jump actor → rocket boots → gun (pull, release) → anchor helper. Every scripted velocity write after the pawn's tick is integrated by the next frame's physics. | CONFIRMED (native) iteration/append rules; STRONG overall (§15) |

## 3. Input path

**G-IN-1** [CONFIRMED (config + src)] The fire action (`GBA_Fire`: left mouse button, gamepad right trigger)
runs `StartFire` on press and `StopFire` on release. `ASAMUPlayerController.StartFire` forwards to the pawn
only if a pawn exists, the controller is not in cinematic mode and the world is not "players only"; there
is no "unpause on fire". The pawn forwards to the weapon unless it is flagged to not fire weapons.
→ Rust: the grapple button is a press/release pair; gate presses on "cinematic mode" and "players only".

**G-IN-2** [CONFIRMED (src, stock `Engine.Weapon`)] Stock weapon flow: a press marks fire mode 0 pending; in
`Active` the weapon enters `WeaponFiring`, whose entry fires immediately and starts a looping 0.1 s
refire-check timer. While the button is held each refire check fires again (a no-op here, G-IN-3); after a
release, the next refire check returns the weapon to `Active`. A press while still in `WeaponFiring` only
marks the mode pending and is serviced at the next refire check (≤ 0.1 s later, frame-quantised by the
timer rule G-TM-4). While the weapon is still equipping (0.33 s after creation) a press is remembered and
serviced when it becomes `Active` [TENTATIVE: equip-state details not read].
→ Rust: weapon sub-state `{Equipping, Active, Firing{refire_timer}}`; this produces the ≤ 0.1 s re-press latency.

**G-IN-3** [CONFIRMED (src, cdo)] The gun acts on a fire only when its latch `bCanGrapple` is set (initially
true); firing clears the latch and performs the instant-hit fire. `StopFire` (button release) sets the latch,
clears the "attempted during this press" flag `bHasGrappled`, and runs the common release (G-RL-1).
Consequence: **exactly one grapple attempt per button press**; holding the button never re-fires.
→ Rust: `on_press: if latch { latch=false; attempt() }`, `on_release: latch=true; release()`.

**G-IN-4** [CONFIRMED (src)] `EnableGrapple(bool)` (Kismet `SeqAct_ToggleGrapple`, save-game load) writes the
same latch and changes the crosshair. Because every button release sets the latch again, **disabling the
grapple this way only swallows the next press**. The effective hard gates are capacity ≥ 1 (G-AC-1) and the
hand not being hidden (G-AC-3). [Whether any level relies on it: UNKNOWN]
→ Rust: keep `enable_grapple` as a one-shot latch, not a persistent disable.

**G-IN-5** [CONFIRMED (src)] Fire processing is synchronous inside the input event: by the time the press
returns, the gun has traced, decided and — on success — switched the pawn to Flying and the controller to
`Grappling` (state changes run their entry code immediately).

## 4. Targeting trace and crosshair

**G-TG-1 Fire trace** [CONFIRMED (src, stock `Engine.Weapon`/`Pawn`/`PlayerController`, `UTPawn`)]
- Start `S` = pawn view location = `Location + (0, 0, EyeHeight) + WalkBob` (`UTPawn` overrides the weapon
  trace start to the pawn view location; `WalkBob` is the view bob of ABILITIES.md §10).
- Direction = unit vector of the camera's cached point-of-view rotation (with aiming help off the controller
  returns the base aim rotation, which the pawn takes from the controller's view point, i.e. the camera
  cache), zero spread. That rotation includes active camera-animation offsets (grapple loop, landing,
  boots) [chain CONFIRMED (src); magnitude and one-frame cache lag TENTATIVE].
- The unit vector is the engine's `vector(rotation)`: `(cp·cy, cp·sy, sp)` with sines and cosines from the
  angle table, which floors pitch and yaw each to a multiple of 4 rotator units (up to 0.016° low;
  ABILITIES.md A-CM-8) [CONFIRMED (native, `FRotator::Vector @ 0x1000FC740`); measured: with the floored
  angles 47 of 52 recorded airborne anchors on static targets lie within 0.05 uu of the ray (median 0.00) at
  ranges up to 4,939 uu; with the exact angles the median distance is 0.74 uu and the largest 1.99. A local
  recount from the eye of the record before the first attached one (pawn location plus recorded eye height)
  along that record's view: floored 47 of 52, truncated towards zero instead 34 (none of the 13 whose yaw is
  negative and no multiple of 4, against 13 of 13 floored), exact angles 5]. The crosshair trace (G-TG-2)
  and the boost aim use the same conversion.
- End `E = S + 16384·dir`. One zero-extent trace that reports actors, flag `TRACEFLAG_Bullet`, issued by the
  pawn (weapon trace owner = instigator), so the pawn itself is not hit [STRONG].
- **What answers the trace** [CONFIRMED (native: the bullet flag is native trace flag 0x20000, which sends
  a static mesh's check to its triangles; PARITY_FINDINGS V3)]: a static mesh's **triangles**, whatever its
  simple-collision switches and whether or not it has a simple body. So the grapple attaches to meshes the
  pawn walks through (the 515 meshes without a body) and to the triangles of a mesh whose pawn collision
  is a coarser body. The level's BSP is asked first and everything else only up to 5 uu beyond the BSP hit
  (NATIVE_PHYSICS.md 10.2).
- **The hit is reported short of the surface** [CONFIRMED (native); measured for triangles]: see G-AT-4.
- The stock instant-hit routine builds an **ordered impact list**: a first hit that is a non-blocking
  `Trigger`/`TriggerVolume` (or an `InteractiveFoliageActor`) is recorded and the trace continues behind it;
  portals are traced through. **Every impact in the list is evaluated in order** (§5) [CONFIRMED (src)].
  Whether bullet traces report non-blocking triggers in ASAMU is UNKNOWN (maps contain 4–23 `Trigger`s and
  0–16 `TriggerVolume`s). `ASAMUCheckpoint` uses `COLLIDE_TouchAllButWeapons` and is not hit [STRONG].
- When nothing is hit, the impact has no actor and its location is `E`.
→ Rust: `fire_trace(eye_with_bob, view_dir_incl_camera_anim) -> Vec<Impact>`; until the trigger question is
answered, treat triggers as transparent and flag it in trace comparisons. The direction is
`PlayerState::aim_direction` (`sim::rotator_vector` of the cached view; camera animations are not in it).

**G-TG-2 Crosshair (HUD only)** [CONFIRMED (src)] Every gun tick a second trace to `fMaxDistance + 1000` =
6000 uu decides the crosshair. Outside story mode it turns positive when the hit is closer than 5000 uu to
the eye, grapples remain, the hit component is a static-mesh component, the actor's tag is not
`NotGrappleAble` and the top/bottom-only normal rule passes (strictly `> 0.8` / `< −0.8` here); it turns
negative when out of range, out of grapples or `NotGrappleAble`; **a hit on a non-static-mesh component
(e.g. BSP) within range leaves it unchanged**. In story mode it is positive within `interactRange` (200 uu,
from the eye) of an `ASAMUInteractable_Actor` that still accepts interactions. The crosshair never gates the
real grapple: BSP and non-static-mesh geometry are grappled although the crosshair may say no.
The crosshair's trace is a zero-extent bullet trace like the fire trace [CONFIRMED (src): the same flag
argument], so its hit is reported short of the surface in the same way (G-AT-4).
→ Rust: HUD predicate only (`grapple_gun::crosshair`). It asks `CollisionWorld::trace_line` and measures to
the reported hit (`TraceExtent::Zero` on this trace's own 6000 uu: 4.0 uu before mesh triangles), so a
surface 5002 uu from the eye is in range and one 5006 uu away is not
(`crates/asamu-game/tests/parity_world_check.rs`). Not measured: no recording has the crosshair's state.

## 5. Acceptance (what is grapple-able)

`ProcessInstantHit` evaluates each impact (G-TG-1) with this decision order. "Fail sound" means the fail cue
plays and nothing else happens. [all CONFIRMED (src) unless noted]

| Step | Condition | Outcome |
|---|---|---|
| G-AC-0 | pawn in `StoryState` or `Zooming` | no grapple; if the hit point is within 200 uu of the **pawn centre** (the crosshair uses the eye), the pawn's `Interact` runs — effective only in story/zoom, where it calls `ASAMUInteractable_Actor.InteractWith` (uses counted against `MaxInteractTimes`, default 1, CONFIRMED (cdo); fires `SeqEvent_ActorInteractedWith`) |
| G-AC-1 | capacity ≤ 0 | silently nothing |
|  | already attempted during this press, or used ≥ capacity, or no hit actor, or tag `NotGrappleAble` | fail sound, stop |
| G-AC-2 | already attached, or released earlier in this same gun tick window (G-RL-6), or hand hidden (G-AC-3) | nothing happens, but the press is marked as used (no sound) |
| G-AC-4 | tag `TopOnlyGrappleAble` and hit normal Z < 0.8; or tag `BottomOnlyGrappleAble` and normal Z > −0.8 | silent rejection that returns *before* the press is marked used (harmless: the latch already blocks a second attempt). These tag names occur only in the IceCave name table [CONFIRMED (name census)] |
| G-AC-5 | eye-to-hit distance (eye with bob, recomputed at evaluation) ≥ 5000 | fail sound, press marked used |
|  | otherwise | **attach** (§6); press marked used |

**G-AC-3 Hidden hand.** The "hand hidden" flag becomes true only when the hand is hidden with visibility off
(`HideGrappleGun` with its visibility argument false, e.g. via `SeqAct_ToggleVisibleGrapple`), immediately
or 0.3 s later when animated; the story-mode hide keeps visibility and does **not** set it.

**G-AC-6** Every other actor is grapple-able: world BSP (hit actor = the level's WorldInfo), static meshes,
terrain, movers, pawns/NPCs if the trace reports them [STRONG]. There is **no material or channel filter
beyond the trace flags and the tags above**.

**G-AC-7** Once a press is marked used, later impacts of the same list fail at G-AC-1 (with the fail sound).
→ Rust: a pure `accept(impact, pawn_state, gun_state) -> {StoryInteract, Silent, Fail, Attach{instant_release,
anchor_mode}}` with this order; unit-test every branch.

## 6. Attach

Attaching (`GrappleGun.Grapple` plus the tail of `ProcessInstantHit`) is atomic inside the fire input
event. Its effects grouped by kind; only orderings that change behaviour are stated. [CONFIRMED (src)
unless noted]

Gameplay state:
- **G-AT-1 Budget**: used count +1 (an internal capacity re-check cannot fail after G-AC-1).
- **G-AT-5 Move-input lock**: one level of the stacked move-input lock is removed (counter −1, floor 0). This
  ends a power-leap or rocket-boost lock early (ABILITIES.md §8).
- **G-AT-6 Modes**: pawn physics → Flying, controller → `Grappling`, gun "attached" flag set. For a
  release-instant target the one-shot 0.05 s gun timer `ReleaseInstantTimed` is started right after (G-RL-3).
- **G-AT-4 Anchor point**: `A` = the impact's world hit location, and that is **not on the surface**: every
  line check of the original reports its hit moved back along the trace by an amount that depends on the
  routine that answered and on the trace's length (16 384 uu here), and the hit location is the trace's
  start plus that reported fraction of the trace (NATIVE_PHYSICS.md 10.2; constants read in the user's
  executable):

  | What was hit | Anchor before the surface, along the trace | Confidence |
  |---|---|---|
  | a static mesh's triangles | the smaller of a tenth of the trace and 4.0 uu: **4.0 uu** | CONFIRMED (native); measured: 3.9967 uu (median 3.9988, 3.892 to 4.088) at 47 recorded airborne anchors, ranges 691 to 4,939 uu (PARITY_FINDINGS V16) |
  | BSP | a flat **0.5 uu** | CONFIRMED (native); not measured (no recorded anchor on BSP) |
  | a brush (a volume that blocks the trace) | the smaller of a tenth and 1.0 uu: **1.0 uu** | CONFIRMED (native: one computation for both extents); not measured |

  Everything measured from the anchor follows: the range check (G-AC-5) passes for a surface up to 4 uu
  beyond `fMaxDistance`, and the pull's distance and the proximity release (G-PH-2, G-RL-2) see the anchor
  4 uu nearer than the surface. The original's presses whose first measured distance was 197.0 to 199.9 uu
  released in the press frame (PARITY_FINDINGS P3); with the anchor on the surface they measure 200 to 203
  and stay attached.
  → Rust: `grapple_gun::fire_trace` asks `CollisionWorld::trace_line` (a bullet trace: triangles) and
  places the impact at the reported time (`TraceHit::reported_time` with `TraceExtent::Zero`); the game's
  world answers as the original's world check does (`asamu_game::world`). Tests:
  `crates/asamu-game/tests/parity_world_check.rs` (the anchor 4.0 uu before triangles, and a press 202 uu

- **G-AT-3 Grapple-able targets**: if the target implements `ASAMUGrappleAbleInterface` or carries tag
  `grappleInteractable`, its `Grappled` handler runs (crystals, falling rocks react, §12).
- **G-AT-7 Anchor mode (decided last)**: the anchor follows the target **iff it is an `InterpActor`** (helper
  placed at the hit point and based on it); otherwise the anchor stays at the world hit point. This final
  decision overrides the follow flag the interactable branch of G-AT-3 set earlier, so
  `grappleInteractable`-tagged non-InterpActors and moving `DynamicSMActor`s (`ASAMUFloatingRock`) do not
  carry the anchor. An attach on anything else leaves the helper alone: it stays based on the last
  `InterpActor` it was put on and goes on riding it, unread [CONFIRMED (src); measured on the recording
  KM1 in AG-ParadiseCave: 13 of the 66 attachments are on an `InterpActor`, and in each of them the gun's
  anchor is the helper's location in every frame; in the other 53 the helper is elsewhere (at its
  farthest 1,062 to 56,087 uu from the anchor): at the place it was spawned at before the first such

- **G-AT-8 Following**: every gun tick (attached or not) while the follow flag is set, `A` := helper location.
  The flag is not cleared on release (only cosmetic afterwards). The helper is an actor based on the hit
  actor without a hard attachment, and the engine moves such an actor whenever its base has moved or
  turned, **rigidly** [CONFIRMED (native) `UWorld::MoveActor @ 0x1008E94A0`, the loop over the moved
  actor's attached actors from `0x1008E9E9B`; NATIVE_PHYSICS.md 10.5]:
  - the base's rotation did not change (its three members compared as whole integers): the helper is
    moved by the base's translation;
  - it changed, also when the base only turned where it stands: the helper's location is taken through
    the inverse of the base's old transform (rotation and location) and through its new one, so the
    helper's offset from the base's location keeps its coordinates in the base's frame. The helper's own
    rotation gains the base's change;
  - both transforms come from the 16 384-entry sine table, which floors each angle to 4 units: a turn
    that stays within one such step moves nothing;
  - the base's own base carries the base first: a rock attached to a turning hub is moved by the hub's
    move, and that move of the rock carries the helper.

  The base moves in its own tick (a Matinee mover to its track's value, an actor in the rotating physics

  anchor the gun reads is the helper's place after this frame's move of its base.

  Measured on KM1 (the recorder reads the helper's location and the gun's anchor every frame). The
  helper's path over the 13 stretches between one attach on an `InterpActor` and the next:
  - 2 on lifts that move along one line: straight to within 0.02 uu over 6,443 and 8,086 uu, the
    second the whole length of a lift's Matinee track there (8,086.0 uu);

    (two), the world's Z axis for the rock with a rate of yaw. Radii 2,106 to 5,064 uu, 0.4 to 4.5

- **G-AT-10 Velocity**: unchanged by attaching. Changing physics to Flying or Falling never touches velocity;

## 7. While attached

### 7.1 Controller (`ASAMUPlayerController` state `Grappling`) [CONFIRMED (src)]

**G-PH-1** Per controller tick: view rotation updates from mouse/stick as usual; the acceleration passed to
the pawn is always **zero** (the state never fills its wish vector); the jump-pressed flag is cleared, so
jump presses are discarded; no crouch, no double-click handling. The stock global move writer stores the
zero acceleration in the pawn.
→ Rust: while attached, `pawn.acceleration = 0` and `jump_pressed = false` every tick; look input applies.

### 7.2 Pull (`GrappleGun.Tick` → `UpdateGrapple`) [CONFIRMED (src+bc)]

**G-PH-2** On each gun tick while attached, with `P` = pawn centre (after this frame's pawn physics, §15)
and `A` the anchor, `d = |P − A|` is measured first (it also drives an audio parameter `5000 − d`). Then,
unless the rocket boots are in state `Boosting` or the instant-release timer is pending:

- `V ← V + dt · (10⁷ / d) · (A − P)/d` — an acceleration of **`10⁷/d` uu/s²** toward the anchor (2 000 at
  5000 uu, 10 000 at 1000 uu, 50 000 at 200 uu), applied to velocity only (position moves next frame);
- then, if `d < 200` (the distance measured before the pull): `V ← V / 2` and release (G-RL-2).

While boosting or while an instant release is pending, **neither the pull nor the proximity release
happens**.

### 7.3 Native flying physics (`APawn::physFlying @ 0x100AE1710`) [CONFIRMED (native)]

**G-PH-3** One flying update per tick (no sub-stepping):
1. `AccelDir` = unit(`Acceleration`) (zero here).
2. Velocity update through the UDK velocity routine (vtable +0x9D8 = `AUDKPawn::CalcVelocity`,
   NATIVE_PHYSICS.md §2.1) with `MaxSpeed = AirSpeed` (Pawn+0x344, the field `APawn::GetMaxSpeed` returns for
   `PHYS_Flying`), `Friction = 0.5 × PhysicsVolume.FluidFriction`, fluid = 1, brake = 0, buoyancy = 0. With
   zero acceleration this is `V ← V·(1 − F·dt)²`, `F = 0.15 /s`, then the 3-D clamp
   `|V| ≤ AirSpeed·MaxSpeedModifier = 2000`.
3. **No gravity.**
4. Move once by `(V + ZoneVelocity)·dt` (`ZoneVelocity` = 0 everywhere).
5. Blocking hit: `Floor` = hit normal. With `u = −V̂.z`: if the obstacle is a near-vertical wall
   (`|N.z| < 0.2`) **and** `−0.2 < u < 0.5`, try a step-up with the remaining move (gravity direction
   (0,0,−1)); the height gained by stepping is excluded from the velocity re-derivation. Otherwise: wall
   notification, slide along the surface by `(Δ − N(Δ·N))·(1 − t)` if that does not point backwards; on a
   second hit another notification, two-wall adjustment and one more move. No hit → `Floor = (0,0,1)`.
6. Unless teleported during the move: `V = (Location − OldLocation)/dt`. **Velocity into walls is lost**;
   there is no landing while flying.
7. Constants: 0.5 @ 0x101636054, 0.2 @ 0x1016825B8, −0.2 @ 0x10168F00C, 1e-8 normalisation threshold.

**G-PH-4 AirSpeed** [CONFIRMED (src)] is set to `fGrappleAccel` (2000) by the gun at spawn, again whenever the
"released" flag is cleared (G-RL-6) and by the controller's `ResetPlayer` exec. Nothing else writes it (the
`SetSpeed` cheat changes only ground and water speed), so the cap is constant 2000.

**G-PH-5 Consequences** [model from G-PH-2/3 with the §15 order]
- Not a rope: no length constraint, no tangential preservation, no swing. Each tick adds radial velocity and
  the cap rescales the sum, so perpendicular velocity is progressively replaced; the path curves toward the
  anchor.
- Drag-only terminal speed `10⁷/(0.3·d)` exceeds 2000 for every reachable d, so attached motion is
  **cap-limited**: after physics `|V| ≤ 2000` (this is what moves the pawn); after the gun tick the stored
  velocity is up to `2000 + dt·10⁷/d` (≈ +167 uu/s at 60 fps and 1000 uu, +833 near 200 uu).
- 1-D straight pull from rest (re-simulated in the verification pass): release radius reached after
  ≈ 0.52 / 1.42 / 2.95 s from 1000 / 2500 / 4999 uu at 60 fps; speed after the halving ≈ 1210–1220 /
  1435–1460 / 1945–2005 uu/s at 120 / 60 / 30 fps. To be trace-verified.

**G-PH-6 Blocked pulls** [CONFIRMED (src)]: if geometry prevents reaching 200 uu, the pawn stays attached and
pressed against the obstacle, sliding as G-PH-3 allows, until another release path triggers. The declared
stuck-detection variables are never used.

**G-PH-7** While attached there is no gravity and no terminal-velocity clamp (flying never calls it).
→ Rust (G-PH-*): a `Flying` mode in `asamu-player` that ports physFlying (single move, step-up rule, slide,
displacement-derived velocity) plus a `GrapplePull` step in the gun update, in the §15 order. Replace the
current rope model (`RopeMode`, `enforce_rope`, `min_rope_length`); keep the cap as a parameter sourced from
`fGrappleAccel`.

## 8. Release paths

**G-RL-1 Common release** (`GrappleGun.ReleaseGrappleButton`; ignored when not attached) [CONFIRMED (src)]
- Gameplay: pawn physics → Falling; controller → `ReleaseGrapple` (G-RL-7); "attached" flag cleared,
  "released" flag set (G-RL-6). **Velocity and budget are not modified** (G-AT-10 for the physics switch).
- Notifications: Kismet `SeqEvent_PlayerReleasedGrapple` (originator WorldInfo); the grappled actor's
  `UnGrappled` handler if it is grapple-able (crystals uncharge, falling rocks resume).
- Cosmetic: grapple-loop camera animation stopped, beam off, release hand animation, stop sound and
  beam-sound fade-out (0.2 s), pawn script state `Release`.

**G-RL-2 Proximity** (G-PH-2): `d < 200` → velocity halved, then G-RL-1. Only while pulling.

**G-RL-3 Instant-release targets**: the 0.05 s gun timer runs G-RL-1. Timers accumulate frame time and fire
on the first tick where the accumulated time **strictly exceeds** the rate [CONFIRMED (native)
`AActor::UpdateTimers @ 0x100908F50`], after the gun's script tick of that frame [CONFIRMED (native)
`AActor::TickAuthoritative @ 0x100908E50`]. Until then the pawn flies with no pull and no gravity: velocity
only decays by drag and is capped at 2000.

**G-RL-4 Button release**: `StopFire` → G-RL-1 (plus latch reset, G-IN-3).

**G-RL-5 Other callers** [CONFIRMED (src); push values CONFIRMED (cdo)]: every death (`ASAMUPawn.PlayerDied`),
entering story mode, the worm NPC's push (release, set Falling, then add a vector whose X/Y are those of
`unit(player − worm)·500` and whose Z is −50; `PlayerPush` 500, `zVelocityOffset` −50), and the controller's
`ResetPlayer` exec (via `StopFire`). There is **no** release on landing (flying never lands), on collisions,
on a timer for ordinary targets, or when the anchor moves out of range (the 5000 uu check exists only at fire
time and in the rocket-boost loop).

**G-RL-6 No cooldown** [CONFIRMED (src)]: on every gun tick a set "released" flag is cleared (and `AirSpeed`
re-set to 2000); a release inside `UpdateGrapple` is cleared in the same tick. The only lockouts: the refire
timing of G-IN-2 and G-AC-2 — a press processed after a button release but before the gun's next tick
(release and re-press within one frame, weapon already back in `Active`), or right after an instant release
(timer fired at the end of the previous frame's gun tick), is consumed silently.

**G-RL-7 Controller after release** [STRONG; was TENTATIVE] `ReleaseGrapple` defines no per-tick move, so the
controller tick that follows a release runs no move update: no new acceleration (the pawn keeps the zero
from `Grappling`) and no rotation update (that tick's look input is dropped). In that same controller tick
the state's begin code stops the grapple rumble and enters `PlayerWalking` (stock walking/falling control;
its entry clears the jump flag and leaves physics alone because the pawn is falling): state code runs
after the per-tick player update [CONFIRMED (native) `APlayerController::Tick @ 0x10090A760`: input
interactions → `PlayerTick` → state code → timers]. Result: **exactly one controller tick without move and
look**, whether the release came from an input event or from the gun's tick. In the first `PlayerWalking`
move the wish axes come from the pawn rotation *before* that tick's rotation update, which still carries
the pitch it had while flying (the pawn's pitch is zeroed only in Walking/Falling); after removing Z and
normalising this matters only if |pitch| ≥ 90° (view pitch can reach ≈ 98.9°) [CONFIRMED (src)].
→ Rust (G-RL-*): one `release(reason)` with `reason ∈ {Button, Proximity(halve), InstantTimer, Death, Story,
External}`; record it in traces; model the one-tick input gap explicitly.

## 9. Momentum on release

**G-MO-1** [CONFIRMED (src); magnitudes model] No impulse is added at release; the pawn continues with its
velocity under native falling physics (gravity effectively 2 × −520 uu/s², NATIVE_PHYSICS.md §4.6; air
control, ABILITIES.md §4; terminal velocity 10 000). **Corrected:** the handed-over speed is *not* bounded
by 2000. A button release (processed at the start of a frame) hands over the post-pull velocity of the
previous gun tick: up to `2000 + dt·10⁷/d` (≈ 2170 at 60 fps and 1000 uu; ≈ 2830 at 60 fps and ≈ 3670 at
30 fps just outside 200 uu). A proximity release hands over half of that sum (≈ 1000–2000, G-PH-5). Falling
physics has no AirSpeed cap, so this extra speed is kept.

**G-MO-2** [CONFIRMED (src)] Air control after release uses the falling limiter with the current
`GroundSpeed` (440, or 880 only if sprint is still active — jumps remove it) as the "already fast" bound:
above it, air control can steer but not add horizontal speed (NATIVE_PHYSICS.md §4.2).
→ Rust: no release impulse; hand the velocity (including the uncapped last pull) to falling physics.

**G-CT-4 Refills** (used count → 0) [CONFIRMED (src)]:

## 15. Tick order and timing model

**G-TM-1** [CONFIRMED (native, NATIVE_PHYSICS.md §1.1; re-read `AActor::Tick @ 0x10090A210`,
`AActor::TickAuthoritative @ 0x100908E50`)] Within one actor's tick: script `Tick` → latent state code →
timers → physics → `TickSpecial` (pawn eye height). The local player controller instead runs input
interactions → `PlayerTick` (input axes, then the state's `PlayerMove`) → state code → timers.

**G-TM-2 Cross-actor order** [STRONG; was TENTATIVE]
- Native facts [CONFIRMED (native)]: `TickActors<FGlobalActorIterator> @ 0x100912480` walks each level's
  tickable-actor list in index order and ticks pre-async-group actors immediately (other groups are
  deferred); `UWorld::SpawnActor @ 0x1008E5650` appends every spawned actor to the end of that list.
- None of the involved classes changes its actor tick group (all keep the default pre-async group;
  the gun only re-groups its mesh and beam *components*) [CONFIRMED (cdo, src)].
- Spawn order [CONFIRMED (src)]: map-placed actors (movers, crystals, flowers, rocks) are in the map's list;
  then the player controller (login), the pawn, its inventory manager, the power-jump actor, the
  rocket-boots actor, the speed-line cone (all three spawned by the pawn at start), the grapple gun (default
  inventory) and the anchor helper (spawned by the gun).
- Resulting frame [STRONG; input dispatch before the actor ticks is stock engine behaviour, not read]:
  input events (fire/boost/power-jump presses run synchronously; jump only sets a flag) → map actors →
  controller (`PlayerMove`: acceleration, rotation, jump attempt; then its state code) → pawn (state code:
  jump damping; timers: death fade; **physics**; eye height) → power-jump state code → boots state code →
  speed-line cone → **gun** (crosshair, anchor follow, pull, proximity release, counter clamp; then its
  timers: refire check, instant release) → helper.
- Consequences: the pull, boots, power-jump/leap writes and crystal refills computed in frame N are
  integrated by the physics of frame N+1; jump attempts and jump damping act before physics in the same
  frame. A pawn standing on a mover first ticks the mover (NATIVE_PHYSICS.md §1.1), but the pawn is never
  based while flying.

**G-TM-3 Latent sleep** [CONFIRMED (native) `AActor::execPollSleep @ 0x100B35B70`,
`AActor::ProcessState @ 0x100B40E20`] Each tick after the one that issued `Sleep(t)` subtracts `dt` from the
remaining time and wakes when the remaining time is **below half of that tick's dt** (0.5 as a double @
0x1016BC0C0); the overshoot is discarded and the code after the sleep runs in the same tick. Latent loops
are frame-quantised.

**G-TM-4 Timers** [CONFIRMED (native) `AActor::UpdateTimers @ 0x100908F50`] add `dt × timer dilation` to
their count unless paused and fire when `count > rate` (strict); looping timers fire `int(count/rate)` times
and keep the remainder; non-looping timers are removed.

**G-TM-5 State-scoped variables reset on state change** [CONFIRMED (native) `UObject::GotoState @
0x1000B1530` calls `FStateFrame::ClearLocalVars @ 0x1000B1E00`, which zeroes the state-locals buffer,
whenever the target state differs from the current one; re-entering the current state keeps them].
Consequence: every rocket boost starts its timeline at τ = 0, and the power-jump "charged" flag starts false.
→ Rust: a deterministic scheduler with exactly these primitives (latent sleep, timer, state-local reset) and
the explicit actor order above, configurable so trace recordings can confirm it.
